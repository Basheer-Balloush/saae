- Project structure, "where does a new file go", and conventions: see README.md.
- Feedback survey: questions live only in src/features/feedback-survey/lib/feedback-survey.ts; public writes go through server functions (honeypot + IP rate limit), reads/updates only by `admin` role via RLS — keeps contact data out of public queries.
- Course feedback (LMS, after lessons + quiz, before the certificate) is separate from that survey: forms live in the database (`lms_feedback_forms` + frozen `lms_feedback_form_versions`, edited by LMS admins; `DEFAULT_FORM` in src/features/lms/course-feedback/lib/survey.ts only seeds the default). All writes go through server functions; learners read their own response, LMS admins read everything, instructors nothing.
- Coupons and course payments (migrations 20260929150000/150100/170000): every rule is enforced in SQL (`lms_coupon_quote`, `lms_submit_enrollment_request`, `lms_record_payment`, …); src/features/lms/lib/coupons.ts only mirrors the price math for display. Percentage discounts may have an optional whole-pound minimum and an optional maximum, and never exceed the course price. One discount coupon and one recognition code per learner per course, ever; recognition codes mark a course completed (`lms_enrollments.completion_source = 'recognition'`) and skip lessons/quiz but not feedback. Recognition requires a code (no admin shortcut), subject to the code's total use limit. A code used with the enroll form or on a waiting request enrolls for nothing; a learner already enrolled and not yet certified can redeem one too, and what they owe stays. An admin can cancel either (`lms_admin_cancel_recognition`): the first removes the enrollment, the second keeps it and returns the course to the learner's own progress. Payment entries are insert-only; corrections are opposite entries. Learners never read `lms_coupons`; instructors see neither coupons nor payments. Because instructors read `lms_enrollments`, its money columns are hidden from browser roles (migration 20260930120000): `anon`/`authenticated` have SELECT only on the columns granted by name, so `select("*")` on that table is refused, a new column needs its own `GRANT SELECT (column)`, and price, discount, amount due and `completion_source` are read through `lms_enrollment_billing(course)` (own row, or all rows for an admin). PGlite tests for these rules live outside the repo (ask for the harness).
- Guests (migration 20260929160000) are Supabase anonymous users (`auth.users.is_anonymous`, `useLmsAuth().isGuest`). They request courses and learn like anyone; `lms_block_guest_rows` triggers refuse them coupons, certificates, reviews and trainer/intern applications, and `lms_evaluate_certificate` answers `account_required`. Creating an account converts the guest in place: the guest gives a name and an email, and chooses the password on the page the emailed link opens (`lms_guest_upgrades`, then `lms_finish_guest_upgrade`). Never set a guest's password earlier: a password set through the Auth admin API ends all of that user's sessions; signing in to an existing account merges the guest into it (`lms_merge_guest`). Idle guests are deleted nightly by pg_cron (`lms_cleanup_idle_guests`). "Allow anonymous sign-ins" in Supabase Auth must stay on for the guest button to work.
